12장에서, 우리는 마그네틱 디스크와 SSD를 중점으로 물리적 저장장치의 특성에 대해서 배웠습니다. 그리고 RAID구조로 놓여진 다중 디스크를 사용하여 어떻게 빠르고 신뢰할 만한 저장 시스템을 구현할 수 있는지 보았습니다. 이 챕터에서 우리는 저장 매체에 저장되어있는 데이터의 구성과 그 데이터를 어떻게 접근하는지를 중점으로 공부할 것입니다.

## 13.1 Database Storage Architecture

Persistant 데이터는 비휘발성 저장장치(SSD, 자기 디스크)에 저장됩니다. SSD와 자기 디스크는 모두 Block structured인데, 이 말은 데이터가 하나의 블록 단위로 읽거나 쓰여진다는 뜻입니다. 이와 대조적으로 데이터베이스는 블록보다 훨씬 작은 기록들을 다룹니다.
대부분의 데이터베이스는 운영 체제 파일을 기록 저장을 위한 중간 계층으로 사용하여 기본 블록의 일부 세부 사항을 추상화합니다. 그러나 효율적인 액세스를 보장하고 장애로부터의 복구를 지원하려면(19장 후반부에서 살펴보겠지만) 데이터베이스는 블록을 계속 인식하고 있어야 합니다. 따라서 13.2장에서는 블록 구조를 고려하여 개별 기록들이 파일에 저장되는 방식을 살펴봅니다.
일련의 기록들이 주어지면 다음 결정은 파일 구조에서 레코드를 어떻게 구성할 것인가에 달려 있습니다. 예를 들어 정렬된 순서대로, 생성된 순서대로 또는 임의의 순서로 저장할 수 있습니다. 13.3장에서는 몇 가지 대체 파일 조직에 대해 살펴봅니다.
그런 다음 13.4절에서는 데이터 사전에서 데이터베이스가 관계형 스키마와 저장소 조직에 대한 데이터를 구성하는 방법에 대해 설명합니다. 데이터 사전의 정보는 관계의 이름이 주어졌을 때 관계의 레코드를 찾고 검색하는 등 많은 작업에서 매우 중요합니다.
CPU가 데이터에 액세스하려면 데이터가 주 메모리에 있어야 하지만 영구 데이터는 자기 디스크나 SSD와 같은 비휘발성 스토리지에 상주해야 합니다. 일반적인 경우인 주 메모리보다 큰 데이터베이스의 경우, 비휘발성 스토리지에서 데이터를 가져와야 합니다.
비휘발성 저장소에서 데이터를 가져와서 업데이트되면 다시 저장해야 합니다. 13.5절에서는 데이터베이스가 데이터베이스 버퍼라는 메모리 영역을 사용하여 비휘발성 스토리지에서 가져온 블록을 저장하는 방법에 대해 설명합니다.
특정 행의 모든 속성을 함께 저장하는 대신 특정 열의 모든 값을 함께 저장하는 방식으로 데이터를 저장하는 접근 방식은 분석 쿼리 처리에 매우 효과적이라는 것이 밝혀졌습니다. 열 중심 저장이라고 하는 이 아이디어는 섹션 13.6에서 설명합니다.
일부 애플리케이션은 데이터에 매우 빠르게 액세스해야 하며 데이터베이스 전체가 데이터베이스 서버 시스템의 주 메모리에 들어갈 수 있을 정도로 데이터 크기가 작습니다. 이러한 경우 전체 데이터베이스의 복사본을 메모리에 보관할 수 있습니다. 전체 데이터베이스를 메모리에 저장하고 인메모리 데이터 구조와 쿼리 처리 및 데이터베이스에서 데이터의 메모리 잔존을 활용하기 위해 사용하는 기타 알고리즘을 최적화하는 데이터베이스를 주 메모리 데이터베이스라고 합니다. 주 메모리 데이터베이스의 스토리지 구성은 섹션 13.7에서 설명합니다. 개별 바이트 또는 캐시 라인에 직접 액세스할 수 있는 비휘발성 메모리, 즉 스토리지 클래스 메모리가 개발 중이라는 점에 유의하세요. 주 메모리 데이터베이스 아키텍처는 이러한 스토리지에 맞게 더욱 최적화될 수 있습니다.
## 13.5 Database Buffer

서버의 메인 메모리 크기는 시간이 지남에 따라 크게 증가했고, 그로 인해 중간 크기의 데이터베이스가 메모리에 들어갈 수 있었습니다. 그러나 서버는 메모리에 대한 요구 사항이 많기 때문에, 데이터베이스에 할당할 수 있는 메모리 양이 중간 크기의 데이터 베이스보다 훨씬 작습니다. 그리고 많은 대형 데이터베이스는 서버의 사용 가능한 메모리보다 훨씬 큽니다.
따라서 오늘날에도 대부분의 데이터베이스에서, 데이터베이스 데이터는 주로 디스크에 상주하며, 데이터를 읽거나 업데이트하려면 메모리로 가져와야 하고, 업데이트된 데이터 블록은 나중에 다시 디스크에 기록해야 합니다.
디스크에서의 데이터 액세스는 인메모리 데이터 액세스보다 훨씬 느리기 때문에 데이터베이스 시스템의 주요 목표는 디스크와 메모리 간의 블록 전송 횟수를 최소화하는 것입니다. 디스크 액세스 횟수를 줄이는 한 가지 방법은 가능한 한 많은 블록을 주 메모리에 보관하는 것입니다. 목표는 블록에 액세스할 때, 이미 블록이 메인 메모리에 있어서, 디스크 액세스가 필요하지 않는 확률을 최대화하는 것입니다.
모든 블록을 메인 메모리에 보관할 수는 없으므로, 블록을 저장하기 위한 메인 메모리의 사용 가능한 공간 할당을 관리해야 합니다. 버퍼는 디스크 블록의 사본을 저장하는 데 사용할 수 있는 메인 메모리의 일부입니다. 모든 블록의 사본은 항상 디스크에 보관되지만 디스크의 사본은 버퍼에 있는 버전보다 오래된 블록의 버전일 수 있습니다. 버퍼 공간 할당을 담당하는 하위 시스템을 버퍼 관리자라고 합니다.

### 13.5.1 Buffer Manager

데이터베이스 시스템의 프로그램은 디스크에서 블록이 필요할 때 버퍼 관리자에게 요청(즉, 호출)을 합니다.
블록이 이미 버퍼에 있는 경우 버퍼 관리자는 주 메모리에 있는 블록의 주소를 요청자에게 전달합니다.
블록이 버퍼에 없는 경우, 버퍼 관리자는 먼저 버퍼에 블록을 위한 공간을 할당하고, 필요한 경우 다른 블록을 버려서 새 블록을 위한 공간을 만듭니다.
버려진 블록은 가장 최근에 디스크에 기록된 이후 수정된 경우에만 디스크에 다시 기록됩니다.
그런 다음 버퍼 관리자는 요청된 블록을 디스크에서 버퍼로 읽고, 주 메모리에 있는 블록의 주소를 요청자에게 전달합니다. 버퍼 관리자의 내부 작업은 디스크 블록 요청을 발행하는 프로그램에 투명하게 공개됩니다.
운영 체제 개념에 익숙하다면 버퍼 관리자가 대부분의 운영 체제에서 볼 수 있는 가상 메모리 관리자에 지나지 않는다는 것을 알 수 있습니다. 한 가지 차이점은 데이터베이스의 크기가 컴퓨터의 하드웨어 주소 공간보다 클 수 있으므로, 메모리 주소가 모든 디스크 블록을 처리하기에 충분하지 않다는 것입니다. 또한 데이터베이스 시스템을 제대로 서비스하려면 버퍼 관리자는 일반적인 가상 메모리 관리 체계보다 더 정교한 기술을 사용해야 합니다.

#### 13.5.1.1 Buffer replacement strategy

버퍼에 공간이 남지 않으면 새 블록을 읽어들이기 전에 버퍼에서 블록을 퇴거, 즉 제거해야 합니다.
대부분의 운영 체제는 가장 최근에 참조된 블록이 디스크에 다시 쓰여지고 버퍼에서 제거되는 LRU(최소 최근 사용) 방식을 사용합니다.
데이터베이스 애플리케이션의 경우 이 간단한 접근 방식을 개선할 수 있습니다(13.5.2절 참조).

#### 13.5.1.2 Pinned blocks

버퍼가 블록을 가져오면, 데이터베이스 프로세스는 버퍼 메모리에서 블록의 내용을 읽을 수 있습니다.
그러나 블록을 읽는 동안, 동시에 실행되는 다른 프로세스가 블록을 내보내고 다른 블록으로 대체하게 된다면, 이전 블록의 내용을 읽고 있던 리더는 잘못된 데이터를 보게 됩니다. 블록이 내보내질 때 그 블록을 쓰던 중이었다면, 대체 블록의 내용이 손상될 수 있습니다.
따라서 프로세스가 버퍼 블록에서 데이터를 읽기 전에 블록이 퇴출되지 않도록 하는 것이 중요합니다. 이를 위해 프로세스는 블록에서 핀 작업을 실행하고, 버퍼 관리자는 핀된 블록을 절대 퇴출하지 않습니다.
데이터 읽기가 완료되면 프로세스는 언핀 작업을 실행하여 필요할 때 블록을 퇴출할 수 있도록 해야 합니다.
데이터베이스 코드는 너무 많은 블록을 고정하지 않도록 주의해서 작성해야 합니다. 버퍼의 모든 블록이 고정되면 어떤 블록도 퇴출할 수 없고 다른 블록도 버퍼로 가져올 수 없습니다. 이런 일이 발생하면 데이터베이스는 더 이상의 처리를 수행할 수 없게 됩니다!
여러 프로세스가 버퍼에 있는 블록에서 데이터를 읽을 수 있습니다.
각 프로세스는 데이터에 액세스하기 전에 핀 작업을 실행하고 액세스를 완료한 후에는 언핀 작업을 실행해야 합니다.
핀을 실행한 모든 프로세스가 핀 해제 작업을 실행할 때까지 블록을 퇴출할 수 없습니다. 이 속성을 보장하는 간단한 방법은 각 버퍼 블록에 대해 핀 수를 유지하는 것입니다. 각 핀 작업은 카운트를 증가시키고, 핀 해제 작업은 카운트를 감소시킵니다. 핀 수가 0인 경우에만 페이지가 퇴출될 수 있습니다.

#### 13.5.1.3 Shared and Exclusive Locks on Buffer

페이지에서 튜플을 추가하거나 삭제하는 프로세스는 페이지 내용을 이동해야 할 수 있으며, 이 기간 동안 다른 프로세스는 페이지 내용이 일관되지 않을 수 있으므로 페이지 내용을 읽지 않아야 합니다. 데이터베이스 버퍼 관리자는 프로세스가 버퍼에 공유 및 독점 잠금을 설정할 수 있도록 합니다.
잠금은 18장에서 더 자세히 살펴보겠지만, 여기서는 버퍼 관리자의 맥락에서 제한된 형태의 잠금에 대해 설명합니다. 버퍼 관리자가 제공하는 잠금 시스템을 사용하면 데이터베이스 프로세스가 블록에 액세스하기 전에 공유 모드 또는 독점 모드에서 버퍼 블록을 잠그고 나중에 액세스가 완료된 후 잠금을 해제할 수 있습니다. 다음은 잠금에 대한 규칙입니다:

### 13.5.2 Buffer-Replacement Strategies

버퍼의 블록 교체 전략의 목표는 디스크에 대한 액세스를 최소화하는 것입니다.
범용 프로그램의 경우 어떤 블록이 참조될지 정확하게 예측하는 것은 불가능합니다. 
따라서 운영 체제는 블록 참조의 과거 패턴을 향후 참조를 예측하는 지표로 사용합니다.
일반적으로 최근에 참조된 블록은 다시 참조될 가능성이 높다는 가정을 합니다.
따라서 블록을 교체해야 하는 경우 가장 최근에 참조된 블록이 교체됩니다.
이 접근 방식을 가장 최근에 사용된 블록(LRU) 블록 교체 방식이라고 합니다.
LRU는 운영 체제에서 허용되는 대체 방식입니다.
그러나 데이터베이스 시스템은 운영 체제보다 향후 참조 패턴을 더 정확하게 예측할 수 있습니다.
데이터베이스 시스템에 대한 사용자 요청에는 여러 단계가 포함됩니다. 데이터베이스 시스템은 사용자가 요청한 작업을 수행하는 데 필요한 각 단계를 살펴봄으로써 어떤 블록이 필요한지 미리 결정할 수 있는 경우가 많습니다.
따라서 미래를 예측하기 위해 과거에 의존해야 하는 운영 체제와 달리 데이터베이스 시스템은 최소한 단기적인 미래에 관한 정보를 가지고 있을 수 있습니다.

향후 블록 액세스에 대한 정보를 통해 LRU 전략을 개선할 수 있는 방법을 설명하기 위해 SQL 쿼리 처리를 생각해 보겠습니다:

select *
from instructor $\bowtie$ department;

이 요청을 처리하기 위해 선택한 전략이 그림 13.13에 표시된 의사 코드 프로그램에 의해 주어졌다고 가정합니다. (보다 효율적인 다른 전략은 15장에서 살펴볼 것입니다.)

이 예제의 두 관계가 별도의 파일에 저장되어 있다고 가정합니다.
이 예제에서는 instructor의 튜플이 한 번 처리되면 해당 튜플은 다시 필요하지 않다는 것을 알 수 있습니다. 따라서 instructor 튜플의 전체 블록 처리가 완료되면 해당 블록은 최근에 사용되었더라도 주 메모리에서 더 이상 필요하지 않습니다. 버퍼 관리자는 마지막 튜플이 처리되는 즉시 instructor 블록이 차지하는 공간을 비우도록 지시해야 합니다. 이 버퍼 관리 전략을 토스-임시 전략이라고 합니다.

이제 department 튜플이 포함된 블록을 생각해 보겠습니다. instructor relation의 각 튜플에 대해 모든 department 튜플 블록을 한 번씩 검사해야 합니다. 부서 블록의 처리가 완료되면 다른 모든 부서 블록이 처리될 때까지 해당 블록에 다시 액세스할 수 없다는 것을 알고 있습니다.
따라서 가장 최근에 사용된 department 블록이 마지막으로 다시 참조되는 블록이 되고, 가장 최근에 사용된 department 블록이 다음에 참조되는 블록이 됩니다. 이 가정은 LRU 전략의 기초가 되는 가정과 정반대입니다. 실제로 위 절차에서 블록 교체를 위한 최적의 전략은 가장 최근에 사용된(MRU) 전략입니다. department 블록을 버퍼에서 제거해야 하는 경우 MRU 전략은 가장 최근에 사용된 블록을 선택합니다(블록은 사용 중인 동안에는 교체할 수 없음).

```
for each tuple i of instructor do
	for each tuple d of department do
		if i[dept name] = d[dept name]
		then begin
			let x be a tuple deﬁned as follows:
			x[ID] := i[ID]
			x[dept name] := i[dept name]
			x[name] := i[name]
			x[salary] := i[salary]
			x[building] := d[building]
			x[budget] := d[budget]
			include tuple x as part of result of instructor ⋈department
		end
	end
end
```

이 예제에서 MRU 전략이 올바르게 작동하려면 시스템이 현재 처리 중인 department 블록을 고정해야 합니다. 마지막 department 튜플이 처리된 후에는 블록의 고정이 해제되고 가장 최근에 사용된 블록이 됩니다.

버퍼 관리자는 처리 중인 요청에 대해 시스템이 가지고 있을 수 있는 지식을 사용하는 것 외에도 요청이 특정 관계를 참조할 확률에 대한 통계 정보를 사용할 수 있습니다.
예를 들어, 13.4절에서 살펴본 데이터 사전은 데이터베이스에서 가장 자주 액세스되는 부분 중 하나인데, 모든 쿼리를 처리하려면 데이터 사전에 액세스해야 하기 때문입니다.
따라서 버퍼 관리자는 다른 요인으로 인해 제거해야 하는 경우가 아니라면 주 메모리에서 데이터 사전 블록을 제거하지 않아야 합니다. 14장에서는 파일에 대한 인덱스에 대해 설명합니다. 파일에 대한 인덱스는 파일 자체보다 더 자주 액세스될 수 있으므로 일반적으로 버퍼 관리자는 대체 방법이 있는 경우 주 메모리에서 인덱스 블록을 제거하지 않아야 합니다.

이상적인 데이터베이스 블록 교체 전략은 현재 수행 중인 데이터베이스 작업과 향후 수행될 데이터베이스 작업 모두에 대한 지식이 필요합니다. 가능한 모든 시나리오를 잘 처리하는 단일 전략은 알려져 있지 않습니다. 실제로 이 전략의 결함에도 불구하고 놀라울 정도로 많은 데이터베이스 시스템이 LRU를 사용하고 있습니다. 연습 문제와 연습에서는 대체 전략을 살펴봅니다.

버퍼 관리자가 블록 교체를 위해 사용하는 전략은 블록이 다시 참조되는 시점 이외의 요인에 의해 영향을 받습니다. 시스템이 여러 사용자의 요청을 동시에 처리하는 경우, 데이터베이스 일관성을 유지하기 위해 동시성 제어 하위 시스템(18장)이 특정 요청을 지연시켜야 할 수 있습니다. 동시성 제어 하위 시스템에서 어떤 요청이 지연되고 있는지를 나타내는 정보를 버퍼 관리자에게 제공하면, 이 정보를 사용하여 블록 교체 전략을 변경할 수 있습니다. 구체적으로, 활성(지연되지 않은) 요청에 필요한 블록은 지연된 요청에 필요한 블록을 희생하여 버퍼에 유지할 수 있습니다.

크래시 복구 서브시스템(19장)은 블록 교체에 엄격한 제약을 가합니다. 블록이 수정된 경우, 버퍼 관리자는 이전 버전을 파괴할 수 있으므로 버퍼에 있는 블록의 새 버전을 디스크에 다시 쓸 수 없습니다. 대신 블록 관리자는 블록을 쓰기 전에 장애 복구 서브시스템의 허가를 받아야 합니다. 충돌 복구 서브시스템은 요청된 블록을 출력할 수 있는 권한을 버퍼 관리자에게 부여하기 전에 다른 특정 블록을 강제 출력하도록 요구할 수 있습니다. 19장에서는 버퍼 관리자와 장애 복구 서브시스템 간의 상호 작용을 정확하게 정의합니다.
